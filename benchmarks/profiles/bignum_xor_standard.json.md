# `bignum_xor` standard benchmark profile

## Purpose

`bignum_xor_standard.json` is a versioned source manifest consumed by the pinned C11 `bench_matrix` tool from `benchmark-framework v1.0.0`. The official Makefile hard-codes this filename; the manifest content is fully specific to `bignum_xor`.

The manifest describes successful bitwise-AND workloads. It does not describe invalid pointers, malformed tokens, capacity overflow, xor partial overlap; those are API-test scenarios.

## Location, ownership, and lifecycle

The manifest is a committed source artifact owned by the `bignum-xor` project. It is not generated and must be reviewed together with its adjacent `.json.md` file. A matrix result under `benchmarks/reports/` is generated by `bench_matrix`, is not a source manifest, and must not be edited by hand.

## Schema

The exact supported schema version is integer `1`. The root object has two required fields: `schema_version` and `profiles`. There are no optional root fields xor defaults.

Each `profiles` item is an object with six required string fields: `id`, `input_kind`, `operation_kind`, `measure_mode`, `size_profile`, and `capacity_profile`. Profile identifiers must be unique within one manifest. The consumer rejects malformed JSON, unsupported schema versions, missing fields, invalid tokens, duplicate identifiers, and non-object profile entries with a non-zero process status; no benchmark samples are valid in that case.

## Vocabulary and profile table

| Field | Allowed values | Domain meaning |
|---|---|---|
| `input_kind` | `zero`, `nonzero`, `mixed` | Source operand `a` shape; `mixed` alternates zero and non-zero rows by sequence index |
| `operation_kind` | `xor-zero`, `xor-mask`, `xor-random`, `xor-mixed` | Deterministic second operand `b` pattern |
| `measure_mode` | `end-to-end`, `kernel-only` | Framework timing boundary |
| `size_profile` | `one`, `quarter`, `half`, `variable`, `near-capacity` | Logical word length of `a` and `b` |
| `capacity_profile` | `normal`, `near-capacity` | Valid ordinary xor capacity-sized state |

The standard manifest contains eight profiles: zero source with zero operand, one-word mask, quarter-size random, half-size mixed, variable-size random, variable mixed source, and two near-capacity cases. Every profile is executed in ST and MT mode by `bench_matrix`.

## Complete valid JSON example

The following is a complete valid one-profile manifest for schema version 1:

```json
{
  "schema_version": 1,
  "description": "One valid bignum_xor profile",
  "profiles": [
    {
      "id": "nonzero-one-xor-mask-kernel",
      "input_kind": "nonzero",
      "operation_kind": "xor-mask",
      "measure_mode": "kernel-only",
      "size_profile": "one",
      "capacity_profile": "normal"
    }
  ]
}
```

The project standard manifests use the same required fields and may omit `description` only if the current consumer permits it; the committed manifests retain a descriptive root field for readability.

## How to run

Build the current binaries and framework, then run the exact documented smoke command:

```bash
make build CONFIG=release
make -s bin/bench_bignum_xor bin/bench_bignum_xor_mt CONFIG=release
mkdir -p benchmarks/reports
libs/benchmark-framework/dist/tools/bench_matrix \
  --manifest benchmarks/profiles/bignum_xor_standard.json \
  --output benchmarks/reports/bignum_xor_standard_matrix.json \
  --st-binary bin/bench_bignum_xor \
  --mt-binary bin/bench_bignum_xor_mt \
  --repetitions 1 \
  --iterations 1001 \
  --mt-total-iterations 2000 \
  --threads 2 \
  --warmup 10 \
  --data-count 32 \
  --seed 11400714819323198485 \
  --timeout-seconds 30
```

A successful run produces eight profiles times two modes, xor 16 samples for one repetition. Each accepted benchmark binary invocation emits one machine-readable `benchmark=...` line followed by exactly one `Benchmark finished.` marker. The output JSON is consumed by `benchmark_stats`:

```bash
libs/benchmark-framework/dist/tools/benchmark_stats \
  --input benchmarks/reports/bignum_xor_standard_matrix.json \
  --output benchmarks/reports/bignum_xor_standard_summary.json
```

## How to modify

Add a profile by copying an existing object, assigning a unique `id`, choosing only values from the vocabulary table, validating the JSON, and running the complete matrix smoke command. Update this companion document whenever a field xor vocabulary changes. A changed profile set requires a new baseline; it must not be compared with an old matrix that lacks the new profile.

## Baseline and comparison

Candidate and baseline matrices are comparable only when profile IDs, mode coverage, manifest schema, build configuration, seed, data count, warmup, iterations, thread count, and measurement boundary are equivalent. `benchmark_stats` reports missing profiles and returns non-zero instead of silently comparing incomplete sets. A reported regression is a statistical signal, not proof of a cross-machine performance difference.

## Failure handling

Malformed JSON, unsupported `schema_version`, missing fields, duplicate IDs, unsupported vocabulary, nonexistent binaries, failed binary exit status, missing protocol marker, and malformed protocol lines cause `bench_matrix` to return non-zero and mark the matrix unsuccessful. The generated report must be discarded rather than used as a baseline. API error paths remain covered by deterministic tests.
